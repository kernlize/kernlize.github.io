Add a bridge backend ​

The four non-HTTP bridges are complete up to the backend interface they call. Supplying a backend turns unavailable into a working bridge without touching the parser or the registry, both of which the HTTP bridge already exercises. This how-to supplies a TorrentBackend; the others follow the same shape.

1. Pick the interface ​

BridgeLabelInterfaceMethodLocator fields used
torrentdownloadsTorrentBackendadd(infoHash, trackers, context) → Promise<{ id, name }>infoHash, trackers (may be empty)
nzbdownloadsNzbBackendadd(url, context) → Promise<{ id, name }>url
soulseeksharingSoulseekBackenddownload(user, path, context) → Promise<{ id, name }>user, path
mailmailMailBackendopen(address, subject, context) → Promise<{ id }>address, subject (undefined when absent)

context is the BridgeContext the registry passes through: the requester identity (or 'shell'), an optional AbortSignal and optional headers. Honour the signal when it is present. The bridge reads the fields before calling you and rejects with invalid:locator-missing-<field> if one is missing, so inside the backend they are guaranteed strings; trackers is always a list.

2. Implement it outside the published packages ​

A backend talks to something: a WebTorrent client, a downloader daemon, a mail account. That belongs in the host app (apps/web, or your own page) or in a package of its own with its own dependencies, not in @kernl/bridges, which stays dependency-free. The samples on this page are one module, read top to bottom, and are type-checked by node scripts/check-doc-samples.mjs as part of pnpm docs:check.

ts
import type { BridgeContext, TorrentBackend } from '@kernl/bridges';

interface WebTorrentLike {
  add(magnet: string): { infoHash: string; name: string; ready: Promise<void> };
  remove(torrent: { infoHash: string }): void;
}

export function createWebTorrentBackend(client: WebTorrentLike): TorrentBackend {
  return {
    async add(infoHash, trackers, context: BridgeContext) {
      const magnet = `magnet:?xt=urn:btih:${infoHash}${trackers.map((t) => `&tr=${encodeURIComponent(t)}`).join('')}`;
      const torrent = client.add(magnet);
      context.signal?.addEventListener('abort', () => client.remove(torrent), { once: true });
      await torrent.ready;
      return { id: torrent.infoHash, name: torrent.name };
    },
  };
}

Return a stable id: it is the job's identity in the 202 body the applet receives, and what a future downloads view would use to show state and cancel. The name becomes the job's label. Reject with stable reasons (unavailable:engine-offline, denied:…); the registry reports and rethrows them unchanged (registry.feature, scenario "a bridge failure is reported and rethrown").

3. Hand it to the bridge ​

createTorrentBridge(backend?) takes the backend as an optional argument. Without one it reports { available: false, reason: 'no-backend' } and rejects every resolve() with unavailable:no-backend; with one it reports available and routes resolve() to backend.add.

The shell's bridges are registered by createDefaultBridges in packages/core/src/bridges/default-registry.ts, which createKernl calls when KernlOptions.bridges is absent. Its signature is createDefaultBridges(options?: DefaultBridgesOptions), where the options are the registry's authorize and onResolve plus http for the web bridge. It takes no backends, and a registry cannot replace a bridge it already holds (a second torrent throws invalid:duplicate-bridge torrent). So a host that supplies a backend builds the same five registrations itself, with its backend in place, and passes the registry as KernlOptions.bridges:

ts
import { createKernl, type KernlHost } from '@kernl/core';
import {
  createBridgeRegistry,
  createHttpBridge,
  createMailBridge,
  createNzbBridge,
  createSoulseekBridge,
  createTorrentBridge,
  type BridgeRegistry,
} from '@kernl/bridges';

declare const host: KernlHost;
declare const client: WebTorrentLike;

export function createBridgesWithTorrent(torrent: TorrentBackend): BridgeRegistry {
  const registry = createBridgeRegistry({ onResolve: (event) => console.info('bridge', event) });
  registry.register(createHttpBridge());
  registry.register(createTorrentBridge(torrent));
  registry.register(createNzbBridge());
  registry.register(createSoulseekBridge());
  registry.register(createMailBridge());
  return registry;
}

const kernl = createKernl({ host, bridges: createBridgesWithTorrent(createWebTorrentBackend(client)) });
kernl.bridges.forScheme('magnet')?.availability(); // { available: true }

The web, NZB, Soulseek and mail bridges are the same as the defaults. To ship the backend inside kernl itself, change the torrent registration in createDefaultBridges instead.

Check the bridge's exposure. The torrent bridge declares revealsAddress: true, encryptedInTransit: false, publicActivity: true, which is the truth for a client in a public swarm. The factory does not take an exposure argument, so if your backend changes the truth of any field (a backend that tunnels through a seedbox does not reveal the user's address), register a bridge object with the same resolve and a corrected exposure:

ts
import type { Bridge } from '@kernl/bridges';

export function createTunnelledTorrentBridge(torrent: TorrentBackend): Bridge {
  const stock = createTorrentBridge(torrent);
  return { ...stock, exposure: { ...stock.exposure, revealsAddress: false } };
}

In createBridgesWithTorrent, register createTunnelledTorrentBridge(torrent) in place of createTorrentBridge(torrent).

These three booleans are what the user reads about the bridge: describeBridge renders them in the shell's settings. There is no per-request bridge prompt in this draft, so the description is the only place the user learns what a transfer exposes; it must be right.

4. What already applies, and what does not yet ​

BridgeRegistry.resolve checks availability(), then calls the registry's authorize hook if one was given, before any bridge runs; a denial rejects with denied:bridge. The composed shell wires no BridgeAuthorizer: createKernl uses createDefaultBridges() without authorize, so a request from an applet that holds the resource grant reaches your bridge without a per-request prompt. A host that wants one passes authorize to createBridgeRegistry in the sample above; a consent prompt per host in the shell is on the Roadmap (Alpha status).

The guard's resource:bytes rate and hidden-window allowance apply to resource.* envelopes. A job result reaches kehto's resource service as a 202 Accepted JSON body through createBridgeResourceResolver; the applet that asked receives it. The shell has no downloads list yet, so nothing shows job state to the user; that UI is roadmap work. Every outcome is also reported to onResolve as a BridgeResolveEvent.

5. Specify and document ​

  • packages/bridges/features/backend-bridges.feature already covers the contract with a fake backend: unavailable without a backend, fields handed through, missing fields rejected. Add scenarios for what your backend adds: an aborted context cancels the job; the engine's failure reasons surface unchanged.
  • Move the backend's row from "unavailable" to "available" in Bridges and strike it from the Roadmap.
  • Add a changeset.

The slop gate and the coverage threshold apply to the backend if it lives in packages/. If it lives in apps/web, the Playwright suite in pnpm test:e2e covers it.
